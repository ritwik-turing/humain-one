PD-002 / Evaluation datasetsClarified by Sandip · Acknowledged by Ritwik

One eval set, many execution runs

S
Decision clarified bySandip
Message dateNot provided

The decision

Use a 1..n relationship between an evaluation set and execution runs. An eval set remains unchanged across a group of runs; it is not permanently static.

The reasoning Reasoning supplied to Ritwik by the decision maker

Previous industry expertise.

Sandip’s clarification

“Yes you can consider a 1..n relationship between eval set and execution runs”

Sandip · 6:37 AM

“That does not mean the Eval set is static. It just means that across a few runs the Eval set is static”

Sandip · 6:38 AM

Design interpretation

Reuse a stable, agreed evaluation baseline across runs. When requirements change, use explicit versioning. Keep setup separate from execution and route agent updates through Submit Agent. Ritwik proposed this interpretation at 3:43 PM; Sandip’s reply directly clarifies the eval-set/run relationship. Detailed versioning and edit rules are not specified in this exchange.

Alignment

Ritwik acknowledged Sandip’s clarification at 9:02 AM: “Alright thanks for the alignment”. The earlier blanket restriction should no longer guide the design.

Correction history

Earlier wording: “No dataset mutation flexibility.” This was the initial interpretation reported by Ritwik, not a confirmed blanket prohibition from Sandip. It is retained here as corrected history, not an active requirement or evidence that Sandip reversed a decision.

Ritwik had explained that his prior agentic hackathon experience involved iterating on the eval set during development. His concern was preserving that ability while agreeing a reusable baseline.

Evidence & attribution

Source: Slack exchange pasted by Ritwik into this task. Speaker names and displayed times are retained; the excerpt supplies no calendar dates or message permalink. Initial record: 9 September 2026. This clarification supersedes the initial interpretation of PD-002. Reasoning supplied to Ritwik by the decision maker: previous industry expertise.

PD-003 / Evaluation case editingConfirmed by Ritwik

Manage case content in the backend

R
Decision made byRitwik
Decision date9 September 2026

The decision

Do not provide frontend controls to add, edit or delete individual evaluation cases. Manage case content in the backend. Eval provides read-only previews of imported cases.

The reasoning Supplied directly by Ritwik

Keep the prototype focused; do not optimise for every possible workflow.

Scope to preserve

Source attachment, input mapping and eval-set versioning remain. Updated case content comes from the backend through an updated source. This narrows the frontend editing scope; it does not reverse Sandip’s one-eval-set-to-many-runs clarification in PD-002.

Change history

The V35 interaction audit expanded frontend case deletion and pagination. This decision supersedes that implementation; those controls have been removed.

Evidence & attribution

Direct instruction from Ritwik in this task, recorded 9 September 2026: “Dont allow editing cases in the frontend, they should do it in the backend. let's not optimise for everything here.”

PD-004 / Evaluation terminologyConfirmed by Ritwik

Use “metric” in evaluation flows

R
Decision made byRitwik
Decision date9 September 2026

The decision

Call authored evaluation criteria metrics instead of checks, including the Create metric action. Simplify selection and creation to reduce unnecessary information and clicks.

The reasoning Supplied directly by Ritwik

The check/library/create terminology and dense flow were confusing and overwhelming. A consistent name and simpler flow are easier to understand.

Design interpretation

V35 now opens metric selection directly to available metrics, with selected metrics and a Continue action on the same page. Create metric remains a separate action. This layout is an implementation choice; no new evaluation capability is implied.

Evidence & attribution

Direct request from Ritwik in this task, recorded 9 September 2026: “let's just call it metric” and reduce overwhelm with fewer clicks.

PD-007 / Agent updatesClarified by Ritwik

Restart Submit Agent for updates

R
Decision made byRitwik
Decision date10 September 2026

The decision

Submitting an updated agent from Eval returns the developer to the beginning of the existing Submit Agent flow.

The reasoning Supplied directly by Ritwik

Ritwik clarified that an agent update technically belongs at the start of the submission flow. No further rationale was supplied.

Implementation

Start at Submit Agent step 1. The prototype continues through its existing provisioning, deployment and runtime testing stages before returning to the saved evaluation. Preserve the eval set, metric definitions and earlier run evidence. These stage transitions are simulated; no real deployment occurs.

Clarification history

PD-002 already described routing updates through Submit Agent as a design interpretation. This clarification corrects the shortcut to an isolated replacement uploader; it specifies the beginning of the existing flow as the entry point.

Evidence & attribution

Direct instruction from Ritwik in this task, recorded 10 September 2026: “Submitting an updated agent should technically happen by going to the start of the submit agent flow again”.

Automatic names and Save and run

Decision made byRitwik
Decision date11 September 2026

The decision

Automatically name saved setups Eval set 1, Eval set 2, and executions Run 1, Run 2. Remove the required description and combine saving and starting execution into Save and run. Renaming remains optional.
