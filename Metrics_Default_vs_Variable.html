Which metrics are default, and which are a choice

Research note for the eval workstream. Written against the metric palette mockup with eight chips.

The answer. A metric's place in the product is decided by one thing: what it needs as input. Not how important it sounds.

Sort the eight chips by that and they fall into five tiers with very different costs and dependencies. Two of them are in the wrong place, one of them cannot run at all without a commitment we have not made yet, and two of them are not metrics.

The eight chips are not the same kind of thing

Presented as identical toggles, they read as eight equivalent choices. They are not. Latency is a number we already have. Safety is a classifier on the output. Accuracy needs somebody to have written down the right answer. Bias needs the whole run done twice. The cost difference across that row is roughly a hundred to one, and the UI hides it.

Safety and Multilingual are in the wrong tier

Both are tier 1. They read the output and nothing else. They do not need to know what the agent is for, they do not need a correct answer, and they work on the first upload from a developer nobody has met. That makes them exactly as ownable by the platform as latency is.

The design problem. Safety is currently an unticked chip. The developer most likely to ship an agent that leaks a citizen's national ID is the developer least likely to tick the box that would have caught it. An opt-in safety check protects the developers who did not need protecting.

Microsoft reached the same conclusion in their own evaluator guidance. Their combining-evaluators advice ends with a line that applies to every application type without exception: add the risk and safety evaluators. They ship ten of them, including one called Sensitive Data Leakage that does precisely the citizen-data job, and one called Indirect Attack for instructions smuggled in through retrieved content.

Multilingual has the same shape and a sharper local case. The coverage line already says Arabic and English. A citizen asks in Arabic and gets English back. That is a failure any agent in the catalogue can commit, it needs no domain knowledge to detect, and it is invisible to all four of the mechanical checks. Saudi dialect is also now covered by published benchmarks rather than being an open research problem, so there is something to test against.

Accuracy is a commitment, not a toggle

The dataset in the mockup reads gov-services-eval · 380 cases. That single line is the biggest architectural claim on the screen, and it is worth being explicit about what it commits us to.

Accuracy is tier 3. It cannot be computed unless somebody has written down what the right answer was. So either the platform owns a labelled dataset for the government services category, or the developer supplies expected answers with their own cases. Those are different products.

The platform-owned version is much stronger, because it is the only way two agents in the same category are ever comparable to a buyer. It is also the only version where a certification badge means anything, since a badge earned against a dataset the developer wrote themselves certifies nothing.

The cost is that the marketplace stops being open-ended. Every category needs somebody to build and maintain a labelled set, and an agent that does not fit a category has no accuracy score at all. That is a real trade, and it is the decision behind the chip.

Bias and Robustness are run strategies, not metrics

Everything else in the palette scores a run that already happened. These two cannot. Bias is measured by counterfactual pairs: run the same case twice with one attribute swapped, name, gender, region, and compare the two answers. Robustness is measured by perturbing the input, typos, rephrasing, adversarial framing, and checking the answer holds.

Both mean the platform generates additional cases and runs them. On 380 cases, bias is 760 runs minimum. That is not a chip that behaves like the others, and ticking it should show a changed case count and a changed cost before the run starts, not after the bill arrives.

Worth keeping. Bias on a government citizen-services marketplace is not an optional nicety, and counterfactual testing is the established method for it. The argument here is about where it sits in the interface, not whether to build it.

Nobody else is doing this, which cuts both ways

Microsoft Marketplace certifies third-party AI apps and agents. Their published certification covers listing metadata, accessibility, webhook and billing correctness, and a security review conducted on documents, data flow diagrams and secret handling. It does not run evaluations on the agent's outputs at all.

The established pattern for third-party agent trust is tiered attestation rather than measurement. Tier one is the vendor self-declaring. Tier two is an accredited third party running a published suite. Tier three adds continuous re-testing. That maps almost exactly onto the four certification tiers Prism already has.

So running real behavioural evaluation at submission would put Humain ahead of the largest agent marketplace in the world. It also means there is no template to copy and no industry default to point at when somebody asks why these metrics and not others.

What I would propose

Four layers, where the layer is decided by the dependency and the interface shows it.

Layer 1. Always on, never configurable.
Tier 0 and tier 1. Finished, stayed on track, tool call success, latency and cost, plus safety, sensitive data leakage, prompt injection, and language match. This is the licence to publish. There is no toggle, because a check the developer can switch off is not a platform guarantee.
Layer 2. On by default for the category, dismissible.
Tier 2 and, where a category dataset exists, tier 3. Accuracy against the category set, relevance, helpfulness. Dismissible because a judge on the wrong domain is worse than no judge, and the developer is the one who knows.
Layer 3. Opt in with the cost on screen.
Tier 4. Bias and fairness, robustness, repeated runs for reliability. Ticking any of these should visibly change the case count and the estimate before the run.
Layer 4. Written by the developer.
Anything needing a domain rule we cannot know. Already deferred in the current release, correctly.

The rule underneath all four: a metric's tier is set by what it needs, and the interface should show that dependency rather than hide it behind a uniform chip. A developer who understands why Accuracy is unavailable for their agent will accept it. One who sees a greyed-out toggle with no explanation will file a ticket.

What would make this evidence rather than reasoning

None of the above is grounded in a single real Humain failure. The tiers come from the input-dependency logic, which is sound, and from what the large platforms ship, which is a reasonable prior. Neither tells us what actually breaks here.

The way to fix that is the same loop we are asking developers to run. Take fifty to a hundred real failures from agents that exist today, whatever Prism has already run, describe each in plain language, then count the categories and mark which are detectable without domain knowledge. A day of work, and it converts every claim in this note into something with a number behind it. It also demonstrates the product's own method, which is a decent thing to have done before the meeting.

Plain words

Reference-free
A check that needs only what came back. No correct answer required. Safety and language match are reference-free.
Reference-based
A check that compares the answer to a correct answer somebody wrote down. Accuracy is reference-based.
Ground truth
The written-down correct answer for a case. Expensive, because a human has to produce it.
Counterfactual pair
The same question asked twice with one detail changed, to see whether the answer should not have changed but did.
Judge
A model asked to score another model's answer. Cheaper than a person, less reliable, and it needs to understand the domain to be worth anything.
Trace
The record of the steps the agent took, not the answer it gave.
