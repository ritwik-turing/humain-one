What this is

The Evaluate step of the developer journey, step 6 of 9. The surrounding flow is unchanged from V12.
Evaluation does not gate publishingThere is no pass bar and no platform minimum. Once a developer has run once, Submit for verification is available whatever the result. The loop has to earn its use by being useful.
Every evaluation metric is deliberately authored and attachedPrism does not infer a universal scorecard from the agent. The developer chooses one of four definition mechanisms, supplies its contract, and attaches that saved definition to an evaluation. What the definition needs determines its case-by-case coverage, not whether it is silently switched on.
Safety is not optional, and that is a deliberate choiceTwo cases in this run pass every mechanical column and are only visible to the answer-reading checks. A check the developer can switch off is not a guarantee the marketplace can make, and Microsoft tells every application type to ship the equivalent evaluators.
Repeated steps and broken endings are worth catching for freeStep repetition is 15.7 percent of observed agent failures and mishandled termination another 12.4 in the MAST taxonomy, about a quarter combined. The mechanical checks catch both at zero cost. They cannot say whether an answer was right, which is the other three quarters.
Correctness is the developer's judgementThe developer writes what went wrong in their own words; we group and count. Judge scores ship labelled as a signal, not a measurement, until judge agreement against a human is run.
The pack says what was not checkedEvery check is listed with what happened to it, including the ones that did not run and why. Silence about a metric reads the same as a pass.
A metric is a prompt, a deterministic function, a REST endpoint, or an agentic oneThose are the four kinds Prism lets you define, the same four it types agents by, and every metric on the setup screen says which it is. Nothing is scored by modality: a metric can only read what the agent returned, so a trace has to come back in the response before it can be scored. Confirmed with Uday Kumar Pabbathi, 1 Sep.
The dataset keeps its own shape, and you name the fields onceThere is no schema file. You upload whatever shape you already have, then name which key is the input, which is the expected output, and which are metadata. Every row in a run shares that shape because every row goes to the same agent. Media is never stored in the dataset; the row carries a link and the agent fetches it.
No pass mark, and that is now a joint decisionPrism has no domain knowledge of your agent, so it cannot say what score is good enough. Automatic metric and threshold suggestions were considered and deliberately deferred past V1, because a suggestion nobody has validated is a second thing to check rather than an answer. The developer reads the numbers.
An evaluation is the saved pairing, a job is one run of itPrism keeps a named evaluation with a description, versions it as a lineage, and lists every job under it with datapoints attempted, duration and score. A job that failed before its first datapoint shows 0 of 380 and no score, and stays in the list. Aggregation is a choice, average or sum, and the scale is a toggle, percent, 0 to 10 or 0 to 1. Metric calibration is the agreement between a judge metric and your own verdicts. All of these are on screen because Uday showed them on 1 Sep.
Every result carries an immutable receiptHumain ONE freezes the exact agent version, dataset snapshot, metric definition IDs and versions, evaluator execution, and run settings at job start. Comparison withholds score deltas when a metric version changed, so evaluator drift cannot be presented as an agent regression. This is our product safeguard around Prism execution, not a claim about an unseen Prism screen.
There is no such thing as an agent type hereA case is an input, an output, an optional expected answer and a trace. Input and output are lists of parts, and every part carries its own type: text, image, video, audio, a document, a table, a structured payload or a raw file. One dataset holds all eight at once. Nothing in the product asks what kind of agent produced them.
Coverage is a count, not a switchEvery metric names the one part it cannot work without, and whether it runs is answered case by case. An expected-output judge runs where an expected output exists. A citizen-actionability judge runs where the output is prose. The number on screen says how many cases each one covered and how many it skipped, because a metric that quietly ran on a third of the set reads the same as one that ran on all of it.
No universal evaluation metricsPrism supplies four ways to define a metric: Prompt, Deterministic, REST API and Agentic. The developer creates a metric or deliberately reuses one from their personal library, then attaches it to an evaluation. A new evaluation starts with zero attached. A saved definition can be reused, but that never means it applies automatically to another agent.
The metric library has provenance, not universal truthDefinitions can be Yours, shared by a Team, or published as a governed HUMAIN template. A template is a reviewed starting point, not a universal score and never an automatic attachment. Nothing is inferred from earlier uploads or selected by a hidden model.
In V15The complete evaluation loop plus a real Snowflake import state machine: provider, credentials, connection validation, object selection, preview, draft field mapping, compatibility recalculation, and explicit mapping confirmation before run.
Execution is per datapointPrism evaluates each datapoint independently and can deliver independent datapoints in parallel. The dataset is never placed into one model context. Input-limit validation belongs before the run; internal transport batching is an engineering concern and does not change a score or the developer flow.
